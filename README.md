# Практика 2–3 — Свой API для панели заявок

**Версия 1.0 · 24.11.2026 · 60 минут вместе с преподавателем.**

Сегодня мы ведём одну заявку через браузер, Node.js и JSON-файл. Работаем небольшими частями: преподаватель показывает действие, вы повторяете, проверяете результат и постепенно пробуете знакомые изменения сами. Не нужно выполнять все шаги вперёд во время показа.

Уже готовы форма, карточки из прошлого занятия, два списка, серверный каркас и обработка ошибок. **GET, POST и несколько соединений намеренно не завершены.** Сообщения «Шаг …» — учебные заглушки, а не поломка установки. Личное ДЗ прошлого занятия не требуется.

| Часть | Шаги | Результат |
| --- | --- | --- |
| Запуск · 3 мин | 0 | Два работающих процесса |
| Получить список · 10 мин | 1–2 | Данные API в карточках |
| Создать заявку · 15 мин | 3–6 | Форма, POST и серверная проверка |
| Сохранить в файле · 10 мин | 7–8 | Данные переживают перезапуск |
| Подтвердить заявку · 10 мин | 9–10 | PATCH и событие компонента |
| Разобрать отказ · 8 мин | 11–12 | Ошибка, причина, восстановление |
| Проверить целое · 4 мин | 13 | Работающий сценарий и объяснение |

В коде ищите **«Шаг N» и именованную метку**. Если инструкция говорит заменить фрагмент, меняйте только строки **между** `// START МЕТКА` и `// END МЕТКА`; сами комментарии оставляйте. Импорты уже подготовлены. Сохраняйте файл после правки.

## 0. Запустите общую основу

Откройте именно папку `practice` (или распакованную контрольную версию) с `package.json`, `src`, `server` и этим README. Нужны **Node.js 22.18+ и npm 10+**; комплект проверяется на Node.js 22.22.2. До занятия выполните:

```bash
node -v
npm -v
npm ci
```

В терминале **А** из этой папки:

```bash
npm run dev:api
```

Ожидание: `API: http://127.0.0.1:3001 · хранилище: memory`. Оставьте процесс работать.

В терминале **Б**, в той же папке:

```bash
npm run dev
```

Откройте [страницу приложения](http://127.0.0.1:5173). На старте видны форма, пустые списки, сумма 0 и сообщение **«Шаг 2: подключите загрузку списка…»**. Форма пока недоступна: список ещё не загружен.

Откройте отдельно [проверку API](http://127.0.0.1:3001/api/health): получите `{"data":{"ok":true,"storage":"memory"}}`. В [проверке через Vite](http://127.0.0.1:5173/api/health) ответ тот же. Браузер посылает `/api` в Vite, а его proxy передаёт запрос Node.js.

**После изменения `server/` или серверного исходного набора:** в А нажмите Ctrl+C и снова выполните `npm run dev:api`. Автоматического перезапуска API нет: так в опыте видно, когда заканчивается жизнь данных в памяти. После frontend-правок обновите страницу; Vite оставьте работать. Команды проверки и опытов выполняйте в третьем терминале **В**.

Если API не стартует, сначала прочитайте ошибку в А и проверьте порт 3001. Если не открывается страница — терминал Б и порт 5173. Порты фиксированы; запуск второй копии поверх первой не нужен. Покажите преподавателю номер шага и ошибку. Пока среда восстанавливается, продолжайте в паре.

## 1. Вместе верните список из GET

**Где:** `server/routes/bookings.ts`, метка **API-GET**, внутри ветки `GET`.

Замените заглушку:

```ts
const bookings = await store.list()
```

`store.list()` получает данные, `200` сообщает об успехе, `sendJson` отправляет ответ. `return` заканчивает обработку этого запроса.

## 3. Вместе проверьте входные данные

**Где:** `server/validation.ts`, функция `validateNewBooking`.

Прочитайте с преподавателем готовую **CHECK-NAME**: тело должно быть объектом, имя — непустой строкой после `trim()`. Тело имеет тип `unknown`, потому что запрос может прислать любой клиент.

По этому примеру замените **CHECK-SEATS**:

```ts
if (typeof seats !== 'number' || !Number.isInteger(seats) || seats < 1 || seats > 5) {
  throw new HttpError(400, 'INVALID_SEATS', 'Введите целое число участников от 1 до 5.')
}
return { name: body.name.trim(), seats }
```

Теперь функция возвращает только проверенные `name` и `seats`. Строка `"3"` не проходит проверку числа, даже если в интерфейсе выглядит как тройка.

Сам POST пока отвечает учебной заглушкой шага 4. Проверим функцию через настоящий запрос сразу после следующего шага; отдельно подключать её не нужно.

## 4. Вместе создайте POST

**Где:** `server/routes/bookings.ts`, **API-POST**.

```ts
const input = validateNewBooking(await readJson(req))
const booking: Booking = {
  id: randomUUID(), name: input.name, seats: input.seats,
  status: 'new', source: 'web',
}
const created = await store.add(booking)
sendJson(res, 201, { data: created })
return
```

Сначала проверяем тело, затем сервер назначает id и статус. `await store.add` завершается **до** ответа `201`. Клиент не назначает себе `confirmed` и не выбирает id.

Перезапустите А. На странице приложения откройте DevTools → Console и выполните:

```js
{
  const response = await fetch('/api/bookings', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ name: 'Проба', seats: 1 }),
  })
  console.log(response.status, await response.json())
}
```

**Ожидание:** 201, в `data` новая заявка с уникальным id, `status: 'new'`, `source: 'web'`. Нажмите «Обновить список»: 3 заявки, участников 3.

Повторите тот же запрос с непустым именем и `seats: 0`. **Ожидание:** 400, `error.code: 'INVALID_SEATS'`, сообщение про диапазон; после обновления всё ещё 3 заявки и 3 участника. Если ошибка про имя, проверьте `name`, иначе опыт проверяет другую ветку.

**Перед следующим шагом:** перезапустите А и обновите список. Пока хранилище в памяти, «Проба» исчезает: снова 2 заявки, 2 участника.

## 5. Вместе соедините форму с POST

Сначала **`src/api/bookings.ts`, CLIENT-CREATE**:

```ts
return request<Booking>('/api/bookings', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(input),

```

Затем **`src/main.ts`, SUBMIT**, внутри `try` функции `submitBooking`:


После запроса добавляем в список **ответ сервера** с его id. Готовый `finally` включает кнопки обратно; успешная ветка сбрасывает форму, ветка ошибки оставляет ввод.

## 7. Вместе завершите чтение и запись файла

**Где:** `server/storage/file-bookings.ts`. Пока режим всё ещё `memory`; дописываем обе функции **до переключения**.

В **FILE-READ**:

```ts
const parsed: unknown = JSON.parse(text)
if (!isBookingArray(parsed)) throw new Error('Файл содержит неверный список заявок.')
return parsed
```

`readFile(..., 'utf8')` выше уже дал строку. `JSON.parse` превращает её в данные, а готовая проверка убеждается, что это массив заявок. Повреждённый файл не заменяется пустым автоматически.

В **FILE-WRITE**:

```ts
await writeFile(temporary, JSON.stringify(rows, null, 2) + '\n', 'utf8')
```

Строку сначала записываем во временный файл. Готовый `rename` заменит рабочий файл после успеха, `finally` уберёт временный. Очередь в `server/storage/index.ts` уже выполняет изменения последовательно.

**Сравните с преподавателем одну запись:**

```json
{"id":"b1","name":"Анна","seats":1,"status":"confirmed","source":"web"}
```

```csv
id,name,seats,status,source
b1,Анна,1,confirmed,web
```

JSON сохраняет структуру объекта и тип числа; CSV представляет таблицу, при чтении которой типы нужно определить. Сейчас используем JSON. Экспорт CSV писать не требуется.

## 9. Допишите отказ PATCH для отсутствующей заявки

**Где:** `server/routes/bookings.ts`, ветка **API-PATCH**. Преподаватель показывает готовый успешный путь: извлечь id → проверить тело → `store.confirm(id)` → вернуть 200.

Внутри `if (updated === null)`, метка **NOT-FOUND**, замените учебную ошибку на `HttpError` со статусом **404**, кодом **NOT_FOUND** и сообщением **«Заявка не найдена.»**. Используйте уже знакомый образец `throw new HttpError(...)` из шага 3.

Перезапустите А. В Console страницы:

```js
{
  const response = await fetch('/api/bookings/missing', {
    method: 'PATCH',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ status: 'confirmed' }),
  })
  console.log(response.status, await response.json())
}
```

**Ожидание:** 404, нужное сообщение, после обновления всё ещё 3 заявки и 5 участников. Ответ 501 означает, что учебная заглушка осталась. Для получения помощи покажите это условие преподавателю.

## 11. Найдите причину отказа и восстановите загрузку

Преподаватель показывает **Шаг 11 · ERROR** в `src/api/bookings.ts`: `fetch` получает HTTP-ответ даже при 400/404/500; готовый код проверяет `response.ok` и выбрасывает ошибку. В `src/main.ts` найдите соответствующие `catch` и `finally`. Код менять не нужно.

Теперь самостоятельно:

1. Остановите А, оставьте Б работать. Нажмите «Обновить список».
2. Посмотрите Network и оба терминала. Vite может вернуть свою HTTP-ошибку, потому что API выключен. Это отличается от 400 с JSON-кодом `INVALID_SEATS`, который выдал сам API.
3. **Ожидание:** сообщение об ошибке, кнопка снова доступна, последний список остаётся с пояснением, что его нужно обновить.
4. Запустите А и нажмите «Обновить список» снова: сообщение «Список загружен.», сохранённые данные на месте.

**Объясните:** какое наблюдение указывает на причину? Не исправляйте это через `mode: 'no-cors'`: такая настройка не запускает остановленный сервер.

## 12. Вместе наблюдайте отказ записи

Это **показ преподавателя**, а самостоятельное повторение — по оставшемуся времени. Метка **Шаг 12 · FAIL-WRITE** находится в `server/storage/file-bookings.ts`.

В В выполните:

```bash
npm run demo:fail-next
```

Предскажите результат. В форме введите **Проверка записи, 1** и отправьте. **Ожидание:** POST → 500, сообщение об ошибке, имя осталось в форме, карточка не появилась; файл остался прежним. Терминал А показывает учебный сбой.

Маркер расходуется одной попыткой записи. Нажмите отправку **ещё раз вручную**: теперь 201 и ровно одна новая карточка. Автоматически повторять POST при ошибке нельзя: сначала выясняем, был ли запрос сохранён.

Если отказ не наступил, проверьте `storage: file`. Для отмены ещё не использованного сбоя: `npm run demo:clear`. Перед финальной проверкой сделаем явный сброс данных.
